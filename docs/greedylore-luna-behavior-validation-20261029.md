## Stage 1: Analyzer production and retirement

The Analyzer runs behind a persistent operator bridge inside production `build_sandbox` and a second bubblewrap namespace that replaces `/dev/shm`. Production `analyze()` constructs the role prompt and evidence inventory; the fixture runner adds the bounded synthetic question, session locations and production resource catalog. The model transport is a collaboration subagent using the bridge, rather than the actual Codex launcher. Its shell remains a descendant of the long-lived, task-bound process for real kernel peer authentication. The collaboration model's other tools are not programmatically disabled; routing is instructed, and the local audit covers bridge calls rather than a complete independently captured model-tool trace.

The inputs include a shard symlink to an explicitly authorized shared-memory target, a real committed candidate, and a checkpoint published through `RuntimeArtifacts` and selected by production checkpoint discovery. Checkpoint payloads are small JSON fixture values named `model.pt` and `rank-0.pt`, not Torch training state. Staged-v2 diagnostic workspace and records use the managed shared-memory namespace. The target and original dynamic paths disappear in the nested role shell; the stable checkpoint view remains available, and managed diagnostic execution restores the declared data target.

## Remaining gaps and interpretation

The test demonstrates that fresh Luna operators can discover and use the mounted data/checkpoint views, inspect returned diagnostic log/result paths, archive small evidence, finish Engineering publication and consume persistent references after role retirement. A stable public reference is the handoff interface; ephemeral `/workspace` aliases and recorded historical host paths do not become the permanent publication address.

Two workflow concerns remain open. First, production Engineer scripts may live under `/tmp/<agent-id>/`, which lacks a run identity. The first completed test demonstrated inherited scripts in a reused directory; the clean repeat avoids that condition rather than fixing production scratch isolation. This can contaminate staged script inventories even when the requested probe itself is newly authored. Cross-run concurrency was not tested. Second, the Analyzer's outer `execution.log` is not automatically part of managed diagnostic publication, and its final free-text narrative still cites unarchived `prompt.txt`. Structured handover references and managed stdout/stderr/results survived; this does not prove that every arbitrary working file or narrative citation will remain readable. The consumer's initial canonical-hash false alarms also show a reader-documentation gap.

This is a CPU fixture with actual model behavior and production-backed interfaces. It does not test the actual model launcher/tool interception, full publication authorization for the Analyzer path, real GPU/NCCL, training quality, measured speed, complete historical Git provenance or an active-run upgrade. No production runtime or prompt code was changed by this testing stage.
